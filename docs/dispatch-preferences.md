# Dispatch preferences

- Supabase remains the subscriber record. Only administrators can read subscribers; public clients cannot read personal unsubscribe tokens.
- A signup inserts a pending subscriber and sends an ownership confirmation using Brevo transactional email. Already confirmed readers receive no redundant email. Pending readers can request another link; signup never reverses an unsubscribe.
- Confirmation links are signed, bound to the deployment origin and current unsubscribe state, and expire in 24 hours. The token is in a URL fragment, removed from the address bar by the confirmation page. An explicit button press and POST are required; opening an email link cannot activate a subscription.
- Rejoining requires a new email confirmation. The database update compares the current consent state so a concurrent unsubscribe wins over a stale confirmation. Confirmation marks the internal Supabase audience verified; it does not send campaigns or add unconfirmed contacts to a marketing list.
- Each subscriber has a separate random unsubscribe token. Curator Studio can copy a personal link using the current site's origin. Preview links are for preview review; use the production studio's links for production email campaigns after this change is released.
- Opening a link changes nothing. The reader must press the unsubscribe button. The endpoint records local suppression immediately and, when configured, requests Brevo email blocklisting. Provider failures produce a retry message instead of claiming complete success.
- Include a personal unsubscribe link in every Dispatch campaign. The application sends confirmation emails but does not send campaigns or automatically transfer the audience to a Brevo marketing list. Brevo's native unsubscribe link should also remain in campaign templates.
- The studio filters confirmed, pending, and unsubscribed readers. The dashboard count includes only confirmed readers who have not unsubscribed.
- Runtime configuration: `BREVO_API_KEY` (Netlify Secret, Functions/runtime scope), with optional `BREVO_SENDER_ID` to select an active verified sender. Without a sender ID, the application accepts an account only when it has exactly one active sender. `VESNA_DISPATCH_ORIGIN` is baked from Netlify's deployment URL; local development can set `DISPATCH_SITE_URL`. `DISPATCH_SIGNING_KEY` is optional; otherwise a purpose-specific signing key is derived from the server-only Supabase service key. Key rotation invalidates outstanding links. No client receives either secret.
- Missing email configuration or provider rejection returns a failure rather than claiming delivery. The pending record stays available for a later retry. No confirmation template ID is needed: the message is included in the application.
- The studio's Check connection action uses an administrator-only endpoint to verify Brevo credentials and sender availability. It sends no email and reveals no secret or sender address. A connected status is not a guarantee of inbox delivery; provider acceptance and inbox delivery are separate checks.
- If a mailing provider has its own unsubscribe flow, reconcile its suppressions into Supabase before using Supabase records for another sending system. This release does not install a provider webhook or an automatic reconciliation job.
- Endpoint rate limits are per server instance, matching the existing signup limiter. Use shared limits when traffic warrants them.
